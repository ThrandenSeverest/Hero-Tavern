## 1. Задача

Сделать Hero Tavern удобным локальным приложением для продолжительных ролевых диалогов и приключений, в котором персонажи:

- помнят историю переписки и не повторяют механически предыдущий ответ;
- соблюдают характер, лор, отношения и ранее произошедшие события;
- естественно продолжают сцену, проявляют инициативу, не превращая каждый ответ в пересказ;
- умеют работать как в обычном **Tavern/RP**, так и в более структурированном **Adventure Mode**;
- используют сменяемые локальные модели, включая отдельную модель для изображений;
- не требуют ручной установки множества зависимостей при обычном использовании.

**Ключевое уточнение:** простая замена Qwen 8B Abliterated более крупной моделью **не гарантирует** устранения повторов. Сначала необходимо проверить передачу истории, настройки генерации и шаблоны сообщений.

## 2. Целевая конфигурация пользователя

| Компонент | Конфигурация |
|---|---|
| GPU | **NVIDIA GeForce RTX 5070** (не Ti) |
| Видеопамять | **12 ГБ GDDR7** |
| Оперативная память | **32 ГБ RAM** |
| Основной сценарий | Локальная генерация для одного пользователя |
| Язык историй | В том числе русский |
| Главная цель | Качество RP, устойчивость контекста и удобство |

**Следствие:** быстродействия GPU достаточно для активного тестирования моделей среднего размера, но **12 ГБ VRAM — главное ограничение**. При выборе квантования учитывать не только файл весов, но и KV-кеш, служебную память движка, длину контекста и дополнительные процессы.

При использовании CUDA необходима актуальная сборка inference-движка с поддержкой архитектуры **Blackwell / compute capability sm_120**. Совместимость конкретной версии следует проверять при установке.

## 3. Что изучено у JuicyChat

JuicyChat интересен как **пример продуктового подхода**, а не как источник единственной идеальной модели.

Публично упоминались Claude Sonnet 4, Claude Sonnet 3.7, DeepSeek R1, Gemini 2.5 Flash, Grok 3 Mini; в обзорах также встречался выбор DeepSeek V3. **Это исторически опубликованные сведения, не доказательство актуального полного списка моделей на октябрь 2026 года.** Собственные/внутренние маршруты моделей JuicyChat полностью публично не раскрыты.

Идеи, которые стоит перенести и улучшить:

1. Несколько моделей под разные сценарии, с возможностью переключения внутри UI.
2. Отдельные настройки температуры, длины ответа и контекста.
3. Постоянная память персонажа и истории, **независимая от окна контекста модели**.
4. Предсказуемая генерация: пользователь видит итоговую реплику, а не внутренние черновики.
5. Удобная карточка персонажа, управляющая поведением, лором и границами его знаний.

Не копировать неподтверждённые сведения о внутренней архитектуре конкурента.

## 4. Подробные профили моделей и параметры запуска

> **Официальный shortlist и ссылки размещены в начале документа, в разделе 0.** Именно на него должен опираться каталог моделей в Hero Tavern. Здесь — технические настройки для реализации, а не ещё одна размытая подборка.

### RP: Rocinante-X 12B v1 — первый выбор

- **Рекомендуемое квантование:** Q5_K_M (**8,73 ГБ весов**); резервный профиль Q4_K_M (**7,48 ГБ**).
- **Контекст для первого запуска:** 8 192 токена для Q5; проверить 16 384 после замера VRAM; Q4 пробовать для 16 384–32 768, если позволяет KV-кеш и движок. Это целевые тесты, **не обещание**, что заявленный объём контекста будет столь же качественным.
- **Задачи:** повседневный RP, прямые реплики персонажей, Tavern Mode, narrator-ответы без скрытого reasoning.
- **Шаблон:** производитель прямо указывает **Mistral v3 Tekken** либо Metharme; **не использовать Mistral v7** и не добавлять ошибочный `[SYSTEM_PROMPT]` для v3. Приоритет — metadata GGUF и рекомендации model card.
- **Стартовые sampling-параметры:** temp 0,8, top_p 0,95, repeat penalty 1,05 (сначала сверить с авторским пресетом); max_new_tokens 350–700 для реплик, по настройке пользователя. DRY-семплер — только при проверенной поддержке и без чрезмерного подавления повторяемых имён/терминов.
- **Критерий отказа от дефолта:** хуже Qwen3 14B на одинаковых русскоязычных сценариях или регулярные повторы/ошибки после исправления prompt pipeline.

### Qwen3 14B Q4_K_M — альтернатива для русского и инструкций

- **Веса:** 9,0 ГБ; запас под KV-кеш ограничен сильнее, чем у Rocinante Q4.
- **Контекст:** старт с 8 192, расширять до 16 384 после замеров. Не обещать 32K на GPU без проверок.
- **Thinking:** для видимой реплики **выключить штатным механизмом модели или настроить парсер reasoning**. Простой поиск подстроки `<think>` не заменяет корректную обработку потока и режимов backend.
- **Назначение:** сюжет с большим числом правил, контроль русского языка, потенциально планировщик в двухэтапной генерации.
- **Проверка:** совместимый Qwen3 chat template, stop tokens и длительность ответа.

### Cydonia 24B / Magidonia 24B — не делать обычными моделями

- **Каждая Q4_K_M:** примерно 14,3 ГБ только файл весов, **больше физической VRAM**. Нужен частичный GPU offload в RAM либо агрессивное уменьшение точности с потерей качества.
- **Для чего:** литературное качество, приключения, отдельные сложные эпизоды и тест альтернативного повествования.
- **Базовая политика:** медленный режим с честной меткой *«выше требования / может быть заметно медленнее»*. Нельзя показывать их как комфортно помещающиеся целиком в 12 ГБ.
- **Magidonia:** создатель рекомендует Mistral v7 Tekken; возможна работа с/без thinking. Не переносить chat template Rocinante на Magidonia.

### Qwen 8B Abliterated и крупный Qwen3-30B-A3B

- **8B:** оставить для baseline и запасного профиля; точный идентификатор репозитория и квантование фиксировать из текущего установленного файла, не угадывать.
- **30B-A3B:** MoE активирует часть параметров, но в памяти должны находиться веса всей модели. Подходящесть для 12 ГБ зависит от GGUF-квантования и offload; **не приоритет сейчас**.

### Что показывать в UI каждой модели

Обязательные поля: `name`, `provider/repository`, `revision`, `download_url`, `quantization`, `file_size`, `license`, `model_family`, `chat_template`, `min/target_vram`, `target_context`, `supported_modes`, `thinking_mode`, `recommended_sampler`, `backend`, `install_status`, `tested_on_this_pc`. Значения памяти с пометкой `оценочно` до локальных измерений.

## 5. Приоритет №1 — исправление истории и повторов

**Наблюдаемая проблема:** без двойного мышления герой часто почти дословно повторяет предыдущую реплику; иногда следует характеру из промпта, но игнорирует реальные события переписки.

### Проверки

1. Логировать реальную последовательность сообщений, отправляемую backend: `system`/`developer` (при наличии), `user`, `assistant`, служебные сообщения — в правильном порядке.
2. Исключить **дублирование последнего user/assistant сообщения** при формировании prompt.
3. Проверить, не используется ли ошибочный chat template для текущей GGUF-модели.
4. Убедиться, что последние N реплик действительно передаются, а не заменяются карточкой персонажа или чрезмерно агрессивным summary.
5. Проверить расчёт токенов и отсечение истории **до**, а не после превышения лимита.
6. Проверить `stop` sequences, EOS, roles, границы think-тегов, максимальную длину ответа и ограничения backend.
7. Понять, не начинает ли клиент повторно генерацию при потоковой передаче или при «Продолжить».
8. Разделить техническую диагностику prompt (доступную пользователю в debug-режиме) и сам текст ответа.

### Правильная сборка контекста

Порядок формирования контекста для каждого ответа:

1. Базовые инструкции системы и режим Tavern / Adventure.
2. Карточка персонажа и обязательные правила поведения.
3. Актуальное состояние сцены: кто присутствует, где находится, что происходит.
4. Проверенные факты из долговременной памяти и трекеров.
5. Краткая сводка более ранней истории.
6. **Последние сообщения без пересказа**, в естественном хронологическом порядке.
7. Текущий запрос пользователя — **ровно один раз**.

Резервировать отдельный бюджет токенов под ответ; при нехватке сначала сжимать старые материалы, **не вырезать последние важные сообщения**. Не смешивать сгенерированные предположения и установленные события.

### Антиповтор

- Детектировать near-duplicate ответы в сравнении с последней репликой модели.
- Если ответ явно повторяет сообщение, предлагать контролируемую **однократную регенерацию** с дополнительным требованием развить сцену (без подмены пользовательского текста).
- Не использовать бесконечный цикл регенерации.
- Следить не только за совпадением слов, но и за сюжетной стагнацией: нет нового действия, реакции или полезного изменения сцены.

## 6. Режимы генерации

### Обычный чат — один проход

- Прямая генерация ответа с полным актуальным контекстом.
- Никаких reasoning/think-блоков в видимом сообщении.
- Дефолт: минимум задержки и естественный диалог.

### Двухэтапная генерация — по выбору

1. **Планировщик** получает карточку, память, актуальную сцену и последние реплики; выдаёт **короткий структурированный план** (проверка непротиворечивости, цели NPC, следующее действие).
2. **Повествователь** получает план в служебном контексте и выдаёт **только финальный художественный ответ**.

Разрешить выбирать одну и ту же или разные модели для планировщика и повествователя. План **не добавлять** в переписку как реплику персонажа и **не выдавать** за событие в мире. Не заставлять генерировать план для каждого короткого сообщения.

### Adventure Mode

Тот же единый движок модели, но больше структурированных слоёв:

- состояние мира, локации и активные NPC;
- журнал событий и открытые сюжетные линии;
- трекеры HP/раны/шрамы/предметы/отношения и прочее по карточке;
- последовательно обновляемые факты о произошедшем;
- выборочные этапы планирования при сложных сценах;
- отдельное подключение генерации изображений.

## 7. Память и трекеры

Выделить отдельное от общего чата хранилище:

- **Краткосрочная память:** последние сообщения в точности.
- **Сводка эпизода:** периодически обновляемый краткий пересказ проверенных событий.
- **Долговременные факты:** устойчивые сведения о персонажах, мире, отношениях.
- **Трекеры:** структурированные значения (`здоровье`, `ранения`, `шрамы`, `инвентарь`, `взаимоотношения` и пользовательские поля).

Трекеры должны обновляться только при подтверждённом событии либо по явному действию пользователя; предусмотреть историю изменений, откат и ручную правку. Новые факты не должны без проверки затирать старые.

Увеличение окна контекста **не заменяет** память. Нужны обе технологии.

## 8. Локальный менеджер моделей (ранняя реализация)

В Hero Tavern предусмотреть интерфейс:

- каталог протестированных моделей с указанием назначения;
- **скачать / приостановить / продолжить / удалить / выбрать** GGUF;
- выбор квантования с понятным предупреждением о памяти;
- локальный путь хранения и просмотр занятого дискового пространства;
- индикатор прогресса скачивания, проверка целостности и восстановление после ошибки;
- запуск совместимого backend (например, актуального `llama.cpp`) без ручной работы с командной строкой;
- явное отображение статуса модели: *не установлена / загружается / готова / запущена / ошибка*;
- ручное изменение контекста, GPU offload, sampling, модели планировщика и модели чата;
- fallback при нехватке VRAM с понятным сообщением, **без незаметного переключения на другой модельный профиль**.

**Важно:** модели загружаются из разрешённых источников; ссылки, лицензии, объём загрузки и требования показываются до установки. Не привязывать UI к одному поставщику API.

### Отдельная генерация изображений

- Свой независимый selector: **текстовая модель** ≠ **модель изображения**.
- В дальнейшем выбор локального / внешнего provider; управление доступными image-моделями.
- Не предполагать, что text GGUF совместима с image backend.
- При запуске изображения учитывать конкуренцию за 12 ГБ VRAM: выгрузка LLM из GPU или очередь задач (по настройке).
- **Начальная рекомендуемая графическая модель утверждена для разработки: SDXL Base 1.0.** Второй кандидат — Stable Diffusion 3.5 Medium, далее FLUX.1-schnell (с оптимизациями под 12 ГБ VRAM) и Illustrious XL как альтернативный стиль. Полный список и прямые ссылки — в разделе 0.
- **Backend изображений для первого запуска:** ComfyUI, запускаемый отдельно от llama.cpp; поддержка загрузки SDXL checkpoint, prompt/negative prompt, seed, шагов, разрешения, истории генераций и отмены.
- **Стартовый профиль SDXL:** 1024×1024, 20–30 шагов, CFG 5–7, 1 изображение; точные параметры проверять под конкретный чекпойнт/самплер и стиль.
- **Стартовый профиль SD3.5 Medium:** ориентироваться на рекомендованный model card режим ~40 шагов, guidance ~4,5; при проблемах с VRAM применять документированные варианты квантования/offload.
- **Не загружать локальные LLM и image model одновременно в 12 ГБ VRAM** без доказанной укладки в память; запускать последовательно с корректным сохранением состояния чата.

## 9. Автоматическая диагностика системы — **поздний этап**

**Сейчас не обязательна для MVP**, потому что приложение в первую очередь создаётся для личного использования.

Впоследствии добавить **«Мастер подбора моделей»**:

1. Определение GPU, VRAM, CUDA/driver/backend compatibility, CPU, RAM и свободного места.
2. Различение общей оперативной памяти и реально доступной свободной RAM/VRAM.
3. Оценка памяти под веса, KV-кеш и дополнительные задачи с запасом безопасности.
4. Рекомендации по моделям и квантованию для трёх профилей: **Быстро / Баланс / Качество**.
5. Небольшой локальный бенчмарк: скорость генерации (`tok/s`), время до первого токена, стабильность при выбранном контексте.
6. Сохранение пользовательского выбора с правом игнорировать авто-рекомендацию.
7. Повторная диагностика по кнопке и при существенных изменениях конфигурации.

Не приравнивать «веса модели помещаются на видеокарте» к «модель комфортно работает с большим контекстом».

## 10. Приёмочные тесты качества RP

Провести одинаковые тестовые диалоги минимум на Qwen 8B Abliterated, Rocinante-X 12B и Qwen3 14B. Для Cydonia и Magidonia — по мере доступности.

**Русскоязычные сценарии:**

1. 30–50 сообщений с постепенным развитием одной сцены.
2. Запоминание факта из первых пяти реплик без прямой подсказки.
3. Три NPC с разными манерами речи: без смешивания ролей.
4. Персонаж получает шрам/ранение — это отражается в следующих сообщениях и трекере.
5. Изменение отношений, подтверждённое сюжетным событием.
6. Десять последовательных «Продолжай» — без дословного самоповтора.
7. Обычный чат против двухэтапной генерации на одинаковой истории.
8. Редактирование/откат реплики: новая ветвь не содержит событий из отменённой.
9. Большая карточка персонажа + длинная история: последние реплики не теряются.

**Измерять:** долю повторов, противоречия фактам, следование карточке, инициативность, естественность русского текста, задержку, токены/с и фактическую VRAM/RAM. Сохранять воспроизводимые seed/настройки там, где backend поддерживает детерминированный запуск.

Критерий выбора основной модели: **лучшее качество RP при комфортной скорости**, а не максимальное число параметров или рекламируемая длина контекста.

## 12. Что **не** входит в это ТЗ прямо сейчас

- Обязательный облачный хостинг модели для всех посетителей.
- Требование поддерживать любой слабый ПК с первого релиза.
- Переписывание существующих экранов без необходимости.
- Удаление старой Qwen до успешного A/B-тестирования альтернатив.
- Заявления, что конкретная модель объективно лучше всех для RP, без собственного теста.
- Автоматическая установка нерассмотренных лицензий/весов без согласия пользователя.

## Итоговое решение

Для **Hero Tavern на RTX 5070 12 ГБ / 32 ГБ RAM** начать с устранения ошибки памяти и повторов. **Rocinante-X 12B Q5_K_M (8,73 ГБ)** — первая рекомендуемая RP-модель, с переходом на **Q4_K_M (7,48 ГБ)**, если контекст не укладывается в VRAM. **Qwen3 14B Q4_K_M (9 ГБ)** — главный конкурент по качеству русского языка и выполнению инструкций. **Cydonia / Magidonia 24B Q4_K_M (по 14,3 ГБ)** — экспериментальные профили с RAM offload. **SDXL Base 1.0 через ComfyUI** — первая рекомендованная модель изображений; **SD3.5 Medium** — её следующий конкурент. **Все прямые ссылки, назначения и приоритеты находятся в разделе 0 в начале файла**.

Встроенную загрузку и смену моделей добавить относительно рано; **автоматический анализ компьютера и персональные рекомендации отложить** до следующего этапа развития продукта.
